# Decisions

Format: **ID — decision** · reason · alternatives.

- **D-01 — Savings, Income, Transfers have `counts_as_spend = 0`; Essentials and Lifestyle = 1.** Spec §6 lists Transfers as "excluded" and "Spent this month" is about outflow on consumption; Savings are shown as a Home bar but don't inflate spend. · Alt: Savings counts as spend (would make saving look like overspending).
- **D-02 — Uncategorised (no category → no group) transactions count as spend.** Spec says pending items still count in totals; hiding un-reviewed purchases would defeat the awareness goal. They appear under the synthetic `uncategorised` bucket. · Alt: exclude until categorised.
- **D-03 — Migration 0001 adds constraints beyond the §6 column list: `NOT NULL`, FK `REFERENCES`, defaults, and `CHECK (amount_minor >= 0 AND amount_sgd_minor >= 0)`.** No columns added/removed. Sign is carried by `is_refund`, as the spend definition says "refunds counted as negatives". · Alt: signed amounts.
- **D-04 — Single deploy via Workers Static Assets** (`assets` in wrangler.jsonc, SPA fallback, `run_worker_first: ["/api/*"]`), not Pages. · Spec allows either; this is one `wrangler deploy`.
- **D-05 — Month summaries are computed in JS from rows via `@okanary/core`** (`summarizeMonth`), not in SQL, so there is exactly one implementation of the spend definition. Personal-scale data (hundreds of rows/month) makes this cheap. · Alt: SQL view duplicating the predicate.
- **D-06 — SGT implemented as fixed UTC+8** (Singapore has had no DST since 1982), cross-checked against `Intl` in tests. · Alt: Intl everywhere (slower, same result).
- **D-07 — FX rates are stored as REAL (spec §6) but converted via scaled BigInt in `convertMinor`**, so money is never float-multiplied. 
- **D-08 — Phase 1 is SGD-first:** non-SGD transactions via the API must supply `amount_sgd_minor` (`fx_source='manual'`); automatic FX arrives in Phase 4.
- **D-09 — IDs are ULIDs** generated in the Worker (sortable, no coordination).
- **D-10 — Transaction delete is a hard delete** in Phase 1 (manual entries); `void` status remains for auto-captured items.
- **D-11 — Branching:** the first scaffold commit (331c240) was accidentally pushed to `main`; all further work goes to `claude/okanary-phases-0-5`. `main` was not rewritten (no force-push without the owner's say-so).
- **D-12 — A bare `$` in a Shortcut amount means SGD; `US$` is USD.** The user is Singapore-based and spec §9 lists `$8.90` as an example. · Alt: USD.
- **D-13 — If a foreign-currency capture has no obtainable FX rate (fresh fetch failed and nothing cached), the transaction is still saved, `status='needs_review'`, `amount_sgd_minor=0`, with a note.** Dropping it would lose the record; 0 SGD is flagged in the review inbox until the user sets the SGD amount. · Alt: reject the request.
- **D-14 — Review inbox = non-void, non-excluded rows that are uncategorised, carry only an AI suggestion (`category_source='ai'`), or are `status='needs_review'`** (+ failed raw_ingest rows). No schema flag exists for "suggestion" so `category_source` carries it. A user category choice sets `category_source='user'`, removing it from the inbox.
- **D-15 — Ingest token:** a token generated/rotated in the app is stored in D1 `settings.ingest_token` and, when present, is the ONLY valid token (rotation revokes the old one, incl. the bootstrap `INGEST_TOKEN` secret). The secret is only a bootstrap value. The Setup page shows it to the Access-authenticated owner. · Alt: secret only (not rotatable from Settings, contradicting spec §5).
- **D-16 — Ingest rate limit is an in-isolate 60/min counter** (best effort). A hard limit needs a Cloudflare WAF rate-limiting rule; documented in the deploy steps.
- **D-17 — Retried identical Shortcut POSTs (same raw payload within 5 min) return the original transaction (HTTP 200) instead of creating a duplicate.** Not the Phase 3 Apple Pay↔email merge.
- **D-18 — `AI` binding is in `wrangler.jsonc` (for deploy) but NOT in `wrangler.dev.jsonc`,** because `wrangler dev` always proxies AI to remote Cloudflare, which is off-limits for local work. The code treats AI as optional; tests inject a fake. Local `npm run dev` therefore has no AI suggestions.
- **D-19 — `merchant` stores the normalised name; `merchant_raw` the text as received/typed**, for manual entries too, so history/rule lookups are consistent. UI shows a title-cased version.
- **D-20 — Custom service worker (`injectManifest`)** for push/notificationclick instead of generateSW.
- **D-21 — Push payload lifestyle total uses the Lifestyle group budget from `budgets` when one exists** (table is read now; budgets UI is Phase 4), else shows spend only.
- **D-22 — Migration `0002_duplicate_candidates.sql` adds table `duplicate_candidates(id, txn_id, other_id, created_at, resolved)`.** Spec §4.3/§7.3 require "Possible duplicate — merge?" review cards but §6 has nowhere to store an uncertain match. A separate table avoids touching `transactions`. · Alt: a `transactions.dup_of` column.
- **D-23 — Merge semantics:** the Apple Pay row survives (keeps id, category, user edits) and takes the email's amount/currency/SGD/fx and the (retained) Apple Pay timestamp; status → `confirmed`; both `raw_ingest` rows point at it; its `source` stays `applepay`. If the email arrives first the email row survives and takes the Apple Pay timestamp/account/category gaps. A merge creates no new row and therefore no second push. Only Apple Pay ↔ email pairs are ever merged (never same-source, never manual entries).
- **D-24 — Auto-merge vs "possible":** auto-merge only when the card is known on both sides and equal, currency equal, amount within 1%, within 30 min, and merchant token-similarity ≥ 0.5. Unknown card on either side, or similarity 0.25–0.5, creates a review card instead of merging.
- **D-25 — Email trust:** From domain on an allow-list (dbs.com, dbs.com.sg, posb.com.sg, citibank.com.sg, citi.com, citibank.com + `ALERT_SENDER_DOMAINS`) AND `Authentication-Results` shows `dkim=pass` with `header.d` aligned to the From domain; otherwise forwarded to `FORWARD_TO` unparsed and not stored. The parsed header From (not the envelope sender) is used because Gmail forwarding rewrites the envelope. UNVERIFIED against real forwarded mail.
- **D-26 — DBS and Citi parsers are UNVERIFIED** (no real samples in `/fixtures` or `worker/fixtures`): written against invented `synthetic-*.txt` fixtures only; a regex miss falls to the Workers AI extraction (saved `needs_review`), then to a `failed` raw_ingest card in the Review inbox.
- **D-27 — Email idempotency by `Message-ID`** stored as the first line of `raw_ingest.payload`. The lookup uses an exact `substr()` comparison because D1 rejects `LIKE` patterns over 50 bytes (found by tests).
- **D-28 — Hourly cron** (`0 * * * *`) promotes Apple Pay `pending` rows older than 24 h to `confirmed` and sends the "no DBS/Citi email for 3 days" alert at most once per silence episode (`alert_log`), and never before the first email has ever arrived.
- **D-29 — `raw_ingest.source` for email is `email:dbs` / `email:citi`** so "last email per bank" needs no extra column.
- **D-30 — Migration `0003_trip_currency_alert_unique.sql`:** (a) `ALTER TABLE trips ADD COLUMN currency TEXT` so Quick add can suggest the trip's currency (spec §7.2) without guessing; (b) `UNIQUE INDEX uq_alert_log(kind, ref, period)` so "once per period" alerts are race-free via `INSERT OR IGNORE`. Both are additive; no §6 column changed or removed.
- **D-31 — Card-cycle "bill" ≠ spend.** The card view shows `billEstimate` = every non-void charge on that card (refunds negative), including excluded/reimbursable/Savings charges but not Income/Transfers (card payments), because that is what the statement will total; the spend-definition figure is returned alongside and the UI notes the difference. All other totals use the spend definition. · Alt: spend definition only (would under-predict the bill whenever a reimbursable expense is on the card).
- **D-32 — Cycle dates:** the open cycle starts the SGT day AFTER the last statement date (spend on the statement day belongs to the closing statement); due date = first `due_day` strictly after the statement date; day 29–31 statement days clamp to month length.
- **D-33 — Budgets resolve by `effective_from`:** the latest row with `effective_from <= month` applies to later months until changed; amount 0 = "no budget from this month". "Copy last month" writes explicit rows for the target month. Budgets exist per spend group and per category (Savings/Income/Transfers can't have budgets in the UI because they aren't spend).
- **D-34 — Alerts:** thresholds default 50/80/100 (configurable 1–200, in Settings → Auto-capture & notifications); evaluated after every transaction write/capture, only for the CURRENT SGT month; a jump over several thresholds logs all but pushes only the highest; each (budget, month, threshold) fires once. Alert = push; the row is written even when push isn't configured.
- **D-35 — Pace state:** "on pace" = within ±5% of the budget of the even-spread line; "ahead" above, "under" below, "over budget" past 100%. Safe-to-spend = floor((budget − spent) ÷ days left including today), never negative.
- **D-36 — Trips auto-tag by date:** any transaction (manual or captured) whose SGT date falls inside a trip's dates gets its `trip_id` unless `trip_id: null` is sent (Quick add "Don't tag"). Exclude-from-monthly arrives in Phase 5.
- **D-37 — FX on manual entry:** a non-SGD manual amount is converted at the cached ECB rate (`fx_source='ecb'`) unless the user types the SGD amount (`'manual'`); with no obtainable rate the API returns 422 and the UI asks for the SGD amount. The hourly cron keeps today's rate warm for currencies used in the last 60 days and the active trip's. Editing a foreign transaction without touching the SGD field never flips `ecb` to `manual`.
- **D-38 — Navigation:** 4 tabs (Home, Activity, Budgets, Reports) around a centre add button (changed in D-46); Review is reached from the Home badge, Settings from the gear on Home, Setup from Settings.
- **D-39 — Trip `exclude_from_monthly` extends the spend definition** (`SpendRow.trip_excluded`; `isSpend(row, {ignoreTripExclusion})`): such rows leave every monthly view (Home, Reports, budgets, alerts, digest) but count in the trip's own total (`tripTotals`) and in the card bill. Spec Phase 5 lists "trips with exclude-from-monthly"; this is the single place it is implemented. Transactions are tagged to trips by date (manual, captured and imported).
- **D-40 — Recurring detection rules:** same normalised merchant; most recent run of ≥3 charges; gaps 25–36 days; amounts within ±15% (min ±S$1) of the run's median; last charge ≤45 days ago; refunds/excluded/reimbursable/void ignored. Runs daily (02:00 SGT) and on demand ("Scan my history now"). New finds are unconfirmed; "Not one" sets `active=0` and is never resurrected; confirmed ones are refreshed. Linked via `transactions.recurring_id`. Monthly cadence only (spec says monthly).
- **D-41 — Cron schedule (UTC):** hourly `0 * * * *` (promote pending, email-silence alert, FX refresh); daily `0 18 * * *` = 02:00 SGT (recurring detection); weekly `0 12 * * SUN` = Sunday 20:00 SGT (digest). The spec's optional 21:00 daily summary is not built. Digest week = Monday–Sunday SGT, once per week via `alert_log('weekly_digest')`, toggle in Setup.
- **D-42 — Statement import:** input is CSV (header auto-detected; signed Amount or Debit/Credit columns; `,` `;` or tab; if >60% of a signed column is negative the sign is flipped) or text pasted from a PDF (lines of `date [date] description amount [CR]`); dates are day-first; year-less dates take the latest non-future year. Reconcile per card within ±4 days: exact or ≤1% amount, or ≤6% when the merchant also looks the same (stricter for SGD-recorded items); greedy one-to-one. Matched → SGD amount corrected to the billed one (`fx_source='statement'`, SGD records get `same`), pending → confirmed; unmatched → added as `source='import'` (rules/history categorisation only, no AI, auto trip-tagged); card payments ignored; ours-not-on-statement reported, never deleted. Re-import is a no-op. Cap 300 rows per request; writes are batched in chunks of 50.
- **D-43 — CSV export** has a UTF-8 BOM (Excel), CRLF, decimal-string amounts (never floats), SGT date/time columns, and a leading apostrophe on cells starting with `= + - @` (formula injection) except plain numbers.
- **D-44 — `formatMoneyShort`** (whole dollars from S$10) is used for the digest so one push doesn't mix "S$128" and "S$96.00".
- **D-45 — PDF import is paste-text, not file parsing:** extracting text from a PDF in the browser/Worker needs a heavy library; the spec allows "PDF text". The UI tells the user to copy the text out of the PDF.
- **D-46 — Visual design "Konbini Clay"** (chosen from six mockups): receipt-paper cards with torn edges on a sky-to-cream dotted page; lilac / peach / mint / sunshine accents; dark mode is deep indigo. Token names in `web/src/index.css` are unchanged, so every page inherits it; new tokens: `--sun` (primary action: +, Save), `--lifestyle-ink`/`--good` (readable text versions of the group colours), `--edge` (the hard paper-edge shadow, also wired to Tailwind `shadow-sm`). `--accent` is now deep lilac for links and selected chips. Fonts (M PLUS Rounded 1c, Share Tech Mono) are bundled with `@fontsource` latin subsets so the PWA works offline; the kanji (今月, お金) fall back to the system rounded Japanese font rather than shipping a CJK subset. `.num` (amounts) is the monospace receipt face; `.big-num` is the one headline figure. Settings moved off the tab bar to a gear on Home to make room for the centre + button. Reset rules (`button { color: inherit }`) moved into `@layer base` so Tailwind text utilities win on buttons (selected chips previously rendered dark text on the accent fill). No logic, API or data change.

## v2 (docs/feature-brief-v2.md, plan in docs/plan-v2.md)

- **D-47 — Weekly allowance rounding is cumulative per month:** a week's part of month M covering days a..b is `R(budget·b/dim) − R(budget·(a−1)/dim)` (R = round half up). Each part is within one minor unit of the exact pro-rata value (the brief's "round per part") and all parts of a month add up to exactly that month's budget, not just "within rounding". · Alt: round each part independently (sum can drift by a few cents).
- **D-48 — Carry-over "within the same month" chains weeks that START in the same calendar month.** The first week starting in a month never inherits; carry = Σ(allowance − spent) of the earlier weeks of the chain (unspent and overspent both carry). Default off. Week labels for `alert_log` are the ISO week (`YYYY-Www`) of the week's first day, which stays unique for any week-start day.
- **D-49 — Nudge gate:** every push except the post-purchase one (budget and weekly alerts, digest, email-health, and all v2 pushes) goes through `worker/src/nudge-gate.ts`: max `nudge_daily_limit` (default 2) per SGT day, none in quiet hours (`quiet_start`–`quiet_end`, default 23:00–08:00). Held pushes live in `push_outbox` (migration 0004) and are flushed by the hourly cron (oldest first, still limited; same `tag` → only the newest is sent; >72 h old → dropped). Over-limit pushes wait for the next day's quiet-hours end. Post-purchase pushes are exempt from both the limit and quiet hours: they answer a purchase David just made. The push row is written even when Web Push isn't configured (as D-34).
- **D-50 — The `implementer` subagent type isn't loaded in this cloud session** (the definition came from PR #2's branch after the session started); task briefs go to a general-purpose agent on Sonnet with the implementer's instructions prepended. Same rules, same review before commit.
- **D-51 — When there is a weekly allowance, Home's Lifestyle card leads with the week** ("This week: S$X left of S$Y · resets Mon", week pace bar with a day-of-7 marker, week-based safe-to-spend), month total smaller below. An overspent week shows amber, never red, and says "Allowance used up for this week. No rush, it resets soon." Without a budget or override the old month card stays.
- **D-52 — "Vs your usual" baselines:** a period "has data" when it contains any row that counts as spend (any category), so a category not bought that month averages in a 0. Month: the last 3 complete months with data within a 12-month lookback; week: the last 4 complete weeks with data within 12 weeks, first k days (k = days elapsed including today, day granularity). "About usual" = strictly less than 5% away; usual 0 with current > 0 reads "above" with no percentage. Excluded trips drop out of both sides through the spend definition. The weekly digest's usual line uses the same Monday-start week as the digest's own total; the Home/Lifestyle-card week line follows the `week_start` setting.
- **D-53 — Tone sweep:** the pre-existing Home line "S$x more than this day last month" and the month-only "over budget" pill now use the amber Lifestyle ink instead of red (brief: amber, not red; never shaming).
- **D-54 — Net worth "you saved" vs "market":** market = revaluation of what was already held on the previous snapshot day (previous quantity × today's price and FX − its previous SGD value), plus FX movement on non-SGD balances, plus the growth part of a manual-asset update; flows = Δnet − market, so the two always add up. Everything David does himself (balance edits, buys/sells, new holdings, card spending, loans) is flow. A manual-asset balance (robo-advisor, fund) may carry `flow_minor` ("of which you added/withdrew"); without it the whole change is flow (the brief's worked example). First snapshot: 0/0. Ranges (1-month, YTD) sum the daily flows/market after the baseline snapshot. Unknown FX → that item counts 0 and is flagged, never a guessed rate.
- **D-55 — Card liabilities** come from the card-cycle data: open-cycle bill + last statement's bill until it is paid. Paid = marked in the app (new table `card_statement_paid`), or the bill is ≤ 0, or Card-payment transactions on that card since the statement cover it. Cards without a statement day: charges since the 1st of the SGT month, labelled "estimate". Bills use `billEstimate` (D-31).
- **D-56 — Prices:** Finnhub `/quote` per ticker, Alpha Vantage `GLOBAL_QUOTE` only for tickers Finnhub failed, one batched CoinGecko `simple/price` in SGD (so crypto needs no FX; `prev_close` null). Keys are optional Worker secrets (missing key → source skipped). Daily job at 06:30 SGT = a 4th cron `30 22 * * *` (free plan allows 5). Hourly retries 07:00–11:00 SGT fetch only symbols still lacking a fresh quote (saves the 25/day Alpha Vantage budget); at 12:00 the last price is carried forward with `stale=1`. A later failure never overwrites a fresh quote of the same day. `price_minor` is integer minor units, so assets priced below S$0.01 lose precision (C10; fine for BTC/ETH-class assets). "Refresh now" = same job, at most once per 5 minutes (manual refreshes only).
- **D-57 — Navigation:** bottom bar is Home · Activity · (+) · Money · Reports. Money has top tabs Net worth / Goals / Plan / Budgets (Budgets moved under Money). Home stays spending-first with one summary line per section; daily net-worth moves appear only on the Net worth screen behind a "Today" tap and are never pushed. Monthly summary push on the 1st at 09:00 SGT (hourly cron), via the nudge gate.
- **D-58 — Goal status:** reached (value ≥ target); on track (projected value at the target date ≥ target); ahead (projected ≥ 5% above target, with the surplus); behind (below target: "+S$X/month" = required − current pace, and the completion month at the current pace, or "not reached within 50 years"). Required monthly is rounded UP to the cent so following it reaches the target. Goals without a date (e.g. the emergency fund) use a 12-month horizon for the arithmetic. Long goals show conservative/base/optimistic at −2/base/+2 percentage points (never below 0%). Growth maths uses JS numbers for the exponents; every money output is an integer.
- **D-59 — Goal value (C11):** Σ share-linked net-worth accounts/holdings (value × share) + Σ earmarks + transferred contributions only when the goal has NO share links (otherwise the transfer lands in a linked account and would be counted twice). Pledged money never counts; it is shown separately. Over-allocation (earmarks plus shares claimed on one account above its balance; shares of one holding/account above 100%) is a warning, not an error.
- **D-60 — Current pace (C12):** (goal value now − goal value at the baseline − market movement on the goal's links since then) ÷ months, baseline = the latest daily goal snapshot on/before today − 3 months (else the earliest one; months clamped to 1..3). Market movement per item comes from consecutive net-worth snapshots (`marketByItem`), so price/FX gains never count as saving. No earlier snapshot → pace unknown (shown as such, treated as 0).
- **D-61 — Underspend pledges:** created at 00:00 SGT on the first day of the week (Monday by default, follows `week_start`) for the week that just ended: max(0, allowance − Lifestyle spent). They go to the goal marked `receives_underspend`; when none is marked, to the highest-priority goal that is behind (the brief's default); no such goal → no pledge. One pledge per week (partial unique index), so the job is safe to run twice. Emergency fund suggestion = 6 × the average monthly Essentials spend of the last up-to-6 complete months with data. "Move to safer funding?" fires once per goal (alert_log `goal_safer_funding`) when its horizon crosses below 2 years while it is linked to holdings or brokerage/crypto accounts.
- **D-62 — Wants:** `decide_after` = 00:00 SGT on (the SGT date the item was added + wait days); the hourly cron flips due items to `ready` and sends ONE batched push for everything that became ready (through the nudge gate, so it lands at 08:00 at the earliest). Default wait 7 days, 30 days above S$200 (setting `want_long_wait_threshold_minor`). Buying before the wait ends asks once and is stored as `bought_early` (migration column, C16), never commented on. Skipping offers a pledge of the price to the receiving goal (the same goal as underspend pledges), one pledge per want; "Not bought this year" = skipped items decided in the SGT calendar year. Transaction match suggestions: SGD amount within ±10% and within 14 days of buying.
- **D-63 — One subscriptions table (C1/C2):** migration 0008 renames the Phase 5 `recurring` table to `subscriptions` in place (ids kept), renames `cadence→cycle`, `next_expected→next_renewal`, `expected_amount_sgd_minor→expected_sgd_minor`, adds the brief's columns plus `pending_price_sgd_minor`, backfills (confirmed → active, unconfirmed → candidate, dismissed → dismissed; source detected; SGD; monthly) and drops `merchant/active/confirmed_by_user`. SQLite rewrites the FK on `transactions.recurring_id`, which keeps its name and now means "subscription id" (verified on local D1). Status adds `candidate` and `dismissed` to the brief's list: a detected item needs confirming, and a dismissed one must never come back (D-40).
- **D-64 — Detection now needs 2 consecutive monthly charges** (brief S; was 3 in Phase 5): gaps 25–36 days, amounts within ±15% (min ±S$1), last charge ≤ 45 days ago. A detected candidate that matches an existing entry (same merchant pattern, or similar name and amount within 15%) is merged into it, never duplicated; one batched "New subscription?" push per scan.
- **D-65 — Plan fixed costs from S:** non-yearly subscriptions at their monthly equivalent, yearly ones as a monthly set-aside (÷ 12, rounded up), so annual renewals are covered without counting anything twice. Totals and plan count `active` and `cancel_intended` (still charging); trials, candidates, cancelled and dismissed don't count.
- **D-66 — Subscription signals:** price-change check on every charge matched to a subscription: |SGD − expected| > max(2%, S$0.50), +3% of expected for foreign-currency charges; flagged with Accept new price / Review. Missing charge (> 7 days late) is a quiet flag, never a push. Trial reminder from 2 days before the end (SGT dates), annual renewal 7 days before, quarterly "Still using?" once per quarter as one batched push; all via the nudge gate. "Cancelling moves 'Goal' N weeks earlier" uses the receiving goal (same as underspend pledges) with the subscription's monthly equivalent added to its pace.
- **D-67 — Receipt emails:** Apple (apple.com / email.apple.com / itunes.com) and service senders (Netflix, Spotify, OpenAI, Anthropic, YouTube; Google only for its Play/payments mailboxes, so Gmail's forwarding-verification mail still forwards) pass the same DKIM-aligned check as bank alerts. The Apple parser is UNVERIFIED (invented `synthetic-apple-receipt*.txt` fixtures; a bare `$` is SGD as in D-12): it labels the APPLE.COM/BILL charge with the same total within ±3 days ("Apple: iCloud+ …"), creates/links the subscription (source `apple_receipt`), and a daily re-match catches receipts that arrive before the card charge (10-day window). Other receipts go through Workers AI extraction into a `candidate` subscription (source `email_receipt`) and a `review` row in the Review inbox. Receipts never push. Statement-imported lines also run the subscription charge hook (recurring charges rarely trigger bank alerts). A charge on a descriptor shared by several subscriptions (APPLE.COM/BILL) is linked to the closest-priced one but never raises a price-change flag.
- **D-68 — Plan engine inputs:** income = base take-home in force for the month (commission never raises the regular budget); fixed = subscriptions (D-65) + Essentials baseline per category (average of the last 3 complete months with data, subscription-linked charges excluded so nothing counts twice), each line overridable (e.g. rent); goals = Σ required monthly in priority order; Lifestyle = the rest. Floor = 60% of the last-3-month Lifestyle average (setting overrides it), cap = average + 10%; with no Lifestyle history there is no floor and no cap (C14). Above the cap the excess goes to goals in priority order up to what each still needs; anything left is shown as unallocated savings. Percentages (needs / savings / wants) use largest-remainder rounding so they always sum to 100; 50/30/20 and 60/20/20 are context only.
- **D-69 — Trade-offs are computed:** "extend dates" pushes back the lowest-priority dated goals one month at a time, at most 10 years each, until the shortfall is covered (it says when it can't); "lower Lifestyle" shows the implied weekly allowance (monthly × 7 ÷ days in month); "use expected commission" appears only with ≥ 3 months of commission history and needs average commission ≥ shortfall ÷ the goals share of the split rule. Accepting a plan writes the month's Lifestyle budget (which A's weekly allowance reads) and each goal's planned monthly; a later manual budget edit shows as "manual".
- **D-70 — Commission split:** default 70% goals / 20% guilt-free / 10% buffer (editable). Goals share: behind goals first, then the rest, each in priority order, up to its gap (target − value − already pledged). Buffer: tops up the emergency fund while it has a gap, otherwise joins the goals waterfall. Every goal part becomes a `commission` pledge on confirm; the guilt-free part becomes a one-off `lifestyle_bonus` on the current week's allowance (C15), so it is spendable right away and doesn't leak into later weeks.
- **D-46 — Weekly cron is written `0 12 * * SUN`:** Cloudflare's cron API rejected `0 12 * * 0` (invalid cron string, code 10100) on the first real deploy; it accepts day names or 1–7.
