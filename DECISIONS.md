# Decisions

Format: **ID — decision** · reason · alternatives.

- **D-01 — Savings, Income, Transfers have `counts_as_spend = 0`; Essentials and Lifestyle = 1.** Spec §6 lists Transfers as "excluded" and "Spent this month" is about outflow on consumption; Savings are shown as a Home bar but don't inflate spend. · Alt: Savings counts as spend (would make saving look like overspending).
- **D-02 — Uncategorised (no category → no group) transactions count as spend.** Spec says pending items still count in totals; hiding un-reviewed purchases would defeat the awareness goal. They appear under the synthetic `uncategorised` bucket. · Alt: exclude until categorised.
- **D-03 — Migration 0001 adds constraints beyond the §6 column list: `NOT NULL`, FK `REFERENCES`, defaults, and `CHECK (amount_minor >= 0 AND amount_sgd_minor >= 0)`.** No columns added/removed. Sign is carried by `is_refund`, as the spend definition says "refunds counted as negatives". · Alt: signed amounts.
- **D-04 — Single deploy via Workers Static Assets** (`assets` in wrangler.jsonc, SPA fallback, `run_worker_first: ["/api/*"]`), not Pages. · Spec allows either; this is one `wrangler deploy`.
- **D-05 — Month summaries are computed in JS from rows via `@okanary/core`** (`summarizeMonth`), not in SQL, so there is exactly one implementation of the spend definition. Personal-scale data (hundreds of rows/month) makes this cheap. · Alt: SQL view duplicating the predicate.
- **D-06 — SGT implemented as fixed UTC+8** (Singapore has had no DST since 1982), cross-checked against `Intl` in tests. · Alt: Intl everywhere (slower, same result).
- **D-07 — FX rates are stored as REAL (spec §6) but converted via scaled BigInt in `convertMinor`**, so money is never float-multiplied. 
- **D-08 — Phase 1 is SGD-first:** non-SGD transactions via the API must supply `amount_sgd_minor` (`fx_source='manual'`); automatic FX arrives in Phase 4.
- **D-09 — IDs are ULIDs** generated in the Worker (sortable, no coordination).
- **D-10 — Transaction delete is a hard delete** in Phase 1 (manual entries); `void` status remains for auto-captured items.
- **D-11 — Branching:** the first scaffold commit (331c240) was accidentally pushed to `main`; all further work goes to `claude/okanary-phases-0-5`. `main` was not rewritten (no force-push without the owner's say-so).
- **D-12 — A bare `$` in a Shortcut amount means SGD; `US$` is USD.** The user is Singapore-based and spec §9 lists `$8.90` as an example. · Alt: USD.
- **D-13 — If a foreign-currency capture has no obtainable FX rate (fresh fetch failed and nothing cached), the transaction is still saved, `status='needs_review'`, `amount_sgd_minor=0`, with a note.** Dropping it would lose the record; 0 SGD is flagged in the review inbox until the user sets the SGD amount. · Alt: reject the request.
- **D-14 — Review inbox = non-void, non-excluded rows that are uncategorised, carry only an AI suggestion (`category_source='ai'`), or are `status='needs_review'`** (+ failed raw_ingest rows). No schema flag exists for "suggestion" so `category_source` carries it. A user category choice sets `category_source='user'`, removing it from the inbox.
- **D-15 — Ingest token:** a token generated/rotated in the app is stored in D1 `settings.ingest_token` and, when present, is the ONLY valid token (rotation revokes the old one, incl. the bootstrap `INGEST_TOKEN` secret). The secret is only a bootstrap value. The Setup page shows it to the Access-authenticated owner. · Alt: secret only (not rotatable from Settings, contradicting spec §5).
- **D-16 — Ingest rate limit is an in-isolate 60/min counter** (best effort). A hard limit needs a Cloudflare WAF rate-limiting rule; documented in the deploy steps.
- **D-17 — Retried identical Shortcut POSTs (same raw payload within 5 min) return the original transaction (HTTP 200) instead of creating a duplicate.** Not the Phase 3 Apple Pay↔email merge.
- **D-18 — `AI` binding is in `wrangler.jsonc` (for deploy) but NOT in `wrangler.dev.jsonc`,** because `wrangler dev` always proxies AI to remote Cloudflare, which is off-limits for local work. The code treats AI as optional; tests inject a fake. Local `npm run dev` therefore has no AI suggestions.
- **D-19 — `merchant` stores the normalised name; `merchant_raw` the text as received/typed**, for manual entries too, so history/rule lookups are consistent. UI shows a title-cased version.
- **D-20 — Custom service worker (`injectManifest`)** for push/notificationclick instead of generateSW.
- **D-21 — Push payload lifestyle total uses the Lifestyle group budget from `budgets` when one exists** (table is read now; budgets UI is Phase 4), else shows spend only.
- **D-22 — Migration `0002_duplicate_candidates.sql` adds table `duplicate_candidates(id, txn_id, other_id, created_at, resolved)`.** Spec §4.3/§7.3 require "Possible duplicate — merge?" review cards but §6 has nowhere to store an uncertain match. A separate table avoids touching `transactions`. · Alt: a `transactions.dup_of` column.
- **D-23 — Merge semantics:** the Apple Pay row survives (keeps id, category, user edits) and takes the email's amount/currency/SGD/fx and the (retained) Apple Pay timestamp; status → `confirmed`; both `raw_ingest` rows point at it; its `source` stays `applepay`. If the email arrives first the email row survives and takes the Apple Pay timestamp/account/category gaps. A merge creates no new row and therefore no second push. Only Apple Pay ↔ email pairs are ever merged (never same-source, never manual entries).
- **D-24 — Auto-merge vs "possible":** auto-merge only when the card is known on both sides and equal, currency equal, amount within 1%, within 30 min, and merchant token-similarity ≥ 0.5. Unknown card on either side, or similarity 0.25–0.5, creates a review card instead of merging.
- **D-25 — Email trust:** From domain on an allow-list (dbs.com, dbs.com.sg, posb.com.sg, citibank.com.sg, citi.com, citibank.com + `ALERT_SENDER_DOMAINS`) AND `Authentication-Results` shows `dkim=pass` with `header.d` aligned to the From domain; otherwise forwarded to `FORWARD_TO` unparsed and not stored. The parsed header From (not the envelope sender) is used because Gmail forwarding rewrites the envelope. UNVERIFIED against real forwarded mail.
- **D-26 — DBS and Citi parsers are UNVERIFIED** (no real samples in `/fixtures` or `worker/fixtures`): written against invented `synthetic-*.txt` fixtures only; a regex miss falls to the Workers AI extraction (saved `needs_review`), then to a `failed` raw_ingest card in the Review inbox.
- **D-27 — Email idempotency by `Message-ID`** stored as the first line of `raw_ingest.payload`. The lookup uses an exact `substr()` comparison because D1 rejects `LIKE` patterns over 50 bytes (found by tests).
- **D-28 — Hourly cron** (`0 * * * *`) promotes Apple Pay `pending` rows older than 24 h to `confirmed` and sends the "no DBS/Citi email for 3 days" alert at most once per silence episode (`alert_log`), and never before the first email has ever arrived.
- **D-29 — `raw_ingest.source` for email is `email:dbs` / `email:citi`** so "last email per bank" needs no extra column.
- **D-30 — Migration `0003_trip_currency_alert_unique.sql`:** (a) `ALTER TABLE trips ADD COLUMN currency TEXT` so Quick add can suggest the trip's currency (spec §7.2) without guessing; (b) `UNIQUE INDEX uq_alert_log(kind, ref, period)` so "once per period" alerts are race-free via `INSERT OR IGNORE`. Both are additive; no §6 column changed or removed.
- **D-31 — Card-cycle "bill" ≠ spend.** The card view shows `billEstimate` = every non-void charge on that card (refunds negative), including excluded/reimbursable/Savings charges but not Income/Transfers (card payments), because that is what the statement will total; the spend-definition figure is returned alongside and the UI notes the difference. All other totals use the spend definition. · Alt: spend definition only (would under-predict the bill whenever a reimbursable expense is on the card).
- **D-32 — Cycle dates:** the open cycle starts the SGT day AFTER the last statement date (spend on the statement day belongs to the closing statement); due date = first `due_day` strictly after the statement date; day 29–31 statement days clamp to month length.
- **D-33 — Budgets resolve by `effective_from`:** the latest row with `effective_from <= month` applies to later months until changed; amount 0 = "no budget from this month". "Copy last month" writes explicit rows for the target month. Budgets exist per spend group and per category (Savings/Income/Transfers can't have budgets in the UI because they aren't spend).
- **D-34 — Alerts:** thresholds default 50/80/100 (configurable 1–200, in Settings → Auto-capture & notifications); evaluated after every transaction write/capture, only for the CURRENT SGT month; a jump over several thresholds logs all but pushes only the highest; each (budget, month, threshold) fires once. Alert = push; the row is written even when push isn't configured.
- **D-35 — Pace state:** "on pace" = within ±5% of the budget of the even-spread line; "ahead" above, "under" below, "over budget" past 100%. Safe-to-spend = floor((budget − spent) ÷ days left including today), never negative.
- **D-36 — Trips auto-tag by date:** any transaction (manual or captured) whose SGT date falls inside a trip's dates gets its `trip_id` unless `trip_id: null` is sent (Quick add "Don't tag"). Exclude-from-monthly arrives in Phase 5.
- **D-37 — FX on manual entry:** a non-SGD manual amount is converted at the cached ECB rate (`fx_source='ecb'`) unless the user types the SGD amount (`'manual'`); with no obtainable rate the API returns 422 and the UI asks for the SGD amount. The hourly cron keeps today's rate warm for currencies used in the last 60 days and the active trip's. Editing a foreign transaction without touching the SGD field never flips `ecb` to `manual`.
- **D-38 — Navigation:** 5 tabs (Home, Activity, Budgets, Reports, Settings); Review is reached from the Home badge, Setup from Settings.
